## Comandos

- `ng serve` / `npm start`: servidor de desarrollo en `http://localhost:4200/` con recarga automática.
- `ng build`: build de producción, con salida en `dist/gestion-usuarios/`. El límite de tamaño del paquete inicial (`budgets` en `angular.json`) es 1 MB de aviso y 2 MB de error: todas las vistas se cargan juntas (no hay carga diferida porque no hay router).
- `ng build --watch --configuration development` / `npm run watch`: build de desarrollo que se recompila al guardar.
- `ng test`: pruebas unitarias con Karma/Jasmine (lanzador de Chrome; por defecto queda observando cambios).
- `ng test --watch=false`: una sola ejecución, útil para verificaciones tipo CI.
- `ng test --include='**/usuarios.component.spec.ts'`: ejecuta un solo archivo de pruebas.
- `ng generate component views/<nombre>`: crea una vista standalone nueva con el estilo actual (ver Arquitectura).

No hay script de lint configurado ni framework de pruebas e2e.

### Backend (`back/`)

API NestJS + PostgreSQL + Redis. Es una copia **sin cambios propios** del repo del equipo (`Downloads/clasificacion/clasificacion`, rama `yeison`, commit `802d563` del 2026-10-21; antes venía de `Downloads/CUOC`, commit `1eb4394`). Para actualizarla se aplica el diff entre commits archivo por archivo (agregados, modificados y borrados de `back/`; `.env`, `node_modules` y `dist` no se tocan) y se regenera `openapi.json` desde `/api/docs-json`. Única diferencia local: `back/tsconfig.json` lleva `"typeRoots": ["./node_modules/@types"]`, porque aquí `back/` vive dentro de la raíz del front y TypeScript cargaba los tipos de Jasmine de `../node_modules`, que chocan con los de Jest (`nest build` daba 30 errores). Corre aparte del front:

- `docker compose up -d db redis` (desde la raíz; Docker Desktop abierto): base en el puerto **5434** del equipo y Redis en el 6379. El volumen `api-clasificacion_pgdata` guarda los datos.
- `cd back && npm run db:migrate`: aplica las migraciones SQL pendientes (`db:migrate:check` solo las lista). Aplicadas hasta la 036 el 2026-10-23. La 029 no pudo pasar dos validaciones expertas de prueba hechas con el formato viejo del front (instrumentos 10 y 12): se movieron a `clasificacion._respaldo_validacion_experta_pre029` y `_respaldo_validacion_experta_campo_pre029`. Respaldo completo de la base y del código anterior en `respaldos/2026-10-23/`.
- `cd back && npm run start` (o `start:dev` con recarga): API en `http://localhost:3000`, Swagger en `/api/docs`. Lee `.env` de la raíz (se crea copiando `.env.example`; no se sube). Variables nuevas, todas con valor por defecto: `COOKIE_SECURE` (true solo con HTTPS), `CORS_ORIGINS`, `API_KEY_BUSCADOR|APE|TENDENCIAS` (consulta desde otros sistemas con `x-api-key`), `API_KEY_LIMITE_POR_MINUTO`, `SIEMBRA_CNO` (en local no está: la siembra del catálogo CNO desde `back/database/siembra/cno.xlsx` queda desactivada; en Docker es `true`).
- `cd back && npx jest`: pruebas unitarias del backend (9 suites); `npm run test:e2e` corre contra un servidor levantado.
- `ng serve` ya reenvía `/api`, `/auth` y `/usuario` al backend (`proxy.conf.json`): así el front y la API comparten origen y la cookie de sesión viaja sola.
- Cuentas sembradas al arrancar: `admin@sena.edu.co`, `analista@…`, `experto@…`, `ciudadano@…`, `ape@…`, `tendencias@…`, con la clave de `SEED_USUARIOS_PASSWORD` (por defecto la del `docker-compose.yml`). La cuenta `ape@` solo entra por el portal APE (`portal: 'ape'`), que este front no tiene.
- Catálogos: se cargan subiendo los Excel por `POST /api/cno/upload`, `/api/cuoc/upload` y `/api/correlativa/upload` (campo `file`, con sesión de administrador o analista).

## Arquitectura

Aplicación Angular 19 con componentes standalone (sin NgModules ni router) llamada `gestion-usuarios`. Es un panel de administración de una sola página. Este proyecto es **Clasificación de Ocupaciones** (SENA, Observatorio Laboral y Ocupacional; `PROJECT_STORAGE_PREFIX` = `clasificacion`): su menú tiene Inicio, Consulta (CNO, CUOC, Correlativa), Diligenciamiento (Análisis, Comparativa, Instrumento 2, Instrumento 3 y Actualización de CNO/CUOC/Correlativa), Estadísticas (Validaciones, Reportes) y Gestión de usuarios, más Perfil (tarjeta del usuario) y Configuración como modal. El backend real está en `back/` y su contrato en `back/openapi.json` (login: `POST /auth/login` con `{ identifier, password }` → `{ user }` y la cookie httpOnly `olo_sesion`; roles `ADMINISTRADOR`, `ANALISTA`, `EXPERTO`, `CIUDADANO`, `APE`, `TENDENCIAS_OCUPACIONES`; listas paginadas `{ data, total, page, limit, totalPages }`). **La app necesita el backend corriendo** (sin él no se puede iniciar sesión). Qué servicios ya lo consumen y cuáles siguen simulados está en "Capa de servicios". El front original del que se copian las pantallas está en `Downloads/clasificacion/clasificacion/front` (Angular 21 + Tailwind; antes `Downloads/CUOC/CUOC/front`).

**Común vs. proyecto.** La app está pensada para reutilizarse en varios proyectos (Tendencias, Clasificación, Intranet) que deben verse iguales. Todo lo propio del proyecto vive en `src/app/proyecto/`: `config.ts` (`PROJECT_STORAGE_PREFIX`, prefijo de las claves de localStorage; distinto por proyecto; y `LOGIN_LINKS`, los botones de la esquina superior izquierda del ingreso que abren en otra pestaña el sitio público y la otra aplicación —aquí "Ir a sitio web" e "Ir a tendencias"—; el ingreso, que es común, pinta los que haya), `menu.ts` (`PROJECT_MENU`: árbol de opciones del menú con texto, ícono en trazos SVG y componente, o `children` si es un grupo desplegable; y `DEFAULT_VIEW`) y `translations.ts` (`PROJECT_TRANSLATIONS`: textos del proyecto, que reemplazan a los comunes si repiten clave, p. ej. `about.appName`), más sus vistas en `src/app/views/`. Todo lo demás (shell, `settings/`, `shared/`, `views/usuarios`, `views/perfil`, estilos) es común y debe quedar **idéntico** en todos los proyectos: una mejora en la parte común se hace en la base y se copia tal cual.

**Cambio de vista sin router.** `app.menu.ts` (común) define los tipos del menú, `ADMIN_MENU` (grupo "Gestión de usuarios" con Usuarios, siempre al final; Perfil no está en el menú, se abre desde la tarjeta del usuario), `buildMenu()` (proyecto + administración), `menuViews()` (las opciones que abren vista, sin grupos) y `menuGroupsOf()` (grupos que contienen una vista). Una opción con `children` es un grupo desplegable (se pueden anidar, p. ej. Diligenciamiento > Actualización): no abre vista, solo muestra u oculta sus subopciones; el menú es un acordeón (pedido por Paola el 2026-10-20 para que no se desplace): `toggleGroup()` abre un grupo y cierra los demás de su mismo nivel (con sus subgrupos), y `switchView()` despliega los que contienen la vista elegida y recoge los otros. Las opciones son compactas (40px de alto) y el menú no muestra barra de desplazamiento (si una pantalla muy baja no alcanza, igual se puede desplazar con la rueda). El primer nivel va en Semibold y las subopciones en Regular; los textos se muestran como están escritos (solo la primera letra en mayúscula). `AppComponent` tiene `currentView: AppView` y `pageView` (la vista del área principal, que abre en `DEFAULT_VIEW`): las vistas del proyecto se pintan con `*ngComponentOutlet` a partir de `PROJECT_MENU` (el shell no las importa) y Usuarios/Perfil con `*ngIf`, porque se comunican con el shell. `switchView()` cambia la vista y la guarda en sessionStorage (`VIEW_STORAGE_KEY` = `<prefijo>_view`): al recargar la página con la sesión abierta se vuelve a esa vista (si sigue existiendo en el menú), y al cerrar o vencer la sesión se olvida, así que un ingreso nuevo abre `DEFAULT_VIEW`. `configuracion` es un caso especial: se abre desde el engranaje de la barra superior (`toggleConfiguration()`, no está en el menú) como modal superpuesto (`configurationOpen`) y la vista de `pageView` sigue montada debajo. Cerrar el modal (X, clic fuera o Esc) llama a `closeConfiguration()`, que descarta el borrador sin guardar y vuelve a esa vista. El botón de las tres rayas de la barra superior (`toggleMenu()`, `menuOpen`) muestra u oculta el menú lateral: en escritorio el contenido ocupa el espacio que deja; hasta 900px (`NARROW_SCREEN_MAX_WIDTH`, igual que en `app.component.css`) el menú empieza cerrado y se abre como panel sobre el contenido, con un fondo que lo cierra, y se cierra solo al elegir una vista o con Esc. El menú lateral muestra el rol como etiqueta bajo el logo y, al pie, la tarjeta del usuario (lleva a Perfil) y "Cerrar sesión" (pide confirmación; ver "Inicio y cierre de sesión").

**Estado.** Los usuarios y el perfil se muestran desde `AppComponent` (`users`, `profileUser`), que los carga al iniciar con `UsuariosService.list()` y `PerfilService.get()`. `UsuariosComponent` se enlaza con `[(users)]`: emite `usersChange` cada vez que reemplaza la lista (al crear), mientras que las ediciones y los cambios de estado actualizan los mismos objetos de usuario con lo que responde el servicio. **Gestión de usuarios según el backend** (`/usuario`; la lista solo la ve el administrador): lista (`GET`; el backend la entrega del más nuevo al más viejo y la pantalla la ordena por id), crea (`POST` con `nombreApellido`, `correo`, `documento`, `telefono` y `rol`, los cinco obligatorios: no se envía contraseña ni usuario), edita nombre, correo, cédula y teléfono (`PATCH /usuario/:id`), cambia el rol (`setRole()`, `PATCH` con `{ rol }`) y activa/desactiva (`PATCH` con `estado: 'active' | 'inactive'`; una cuenta inactiva no puede ingresar). **Nombre y apellido van en un solo campo** (`usuario.nombre_apellido`, migración 036). **Cédula** (`User.document`, 5 a 12 dígitos; se aceptan puntos y se envían quitados): es la contraseña inicial de toda cuenta nueva o importada (queda `debeCambiarContrasena` = `User.mustChangePassword` y debe cambiarla al ingresar). **Usuario de ingreso** lo arma el servidor (`accessUsernameOf()` lo muestra de solo lectura en el formulario): el correo si es `@sena.edu.co`/`@soy.sena.edu.co`; si no, la cédula (por eso, con un correo externo la cédula es obligatoria también al editar). El formulario valida con las mismas reglas antes de llamar al servidor (`formErrorKey()`: obligatorios, formato de correo, cédula, teléfono de 7 a 15 dígitos, correo o cédula repetidos) y, si el servidor rechaza los datos con un motivo propio, lo muestra tal cual (`UserError.serverMessage`). Los roles son los seis del backend (`USER_ROLES`, con los nombres de `ROLE_LABELS`); el backend los responde con claves cortas (`admin`, `analyst`, `expert`, `citizen`, `ape`, `tendencias`). Lo que el backend no tiene se quitó de la pantalla: eliminar (su `DELETE` solo desactiva), restablecer acceso, cambiar la contraseña de otro (la inicial es la cédula; después la cambia su dueño), el solo lectura por usuario y el control del bloqueo temporal de analistas. La cuenta propia no se puede desactivar ni cambiar de rol (`isOwnAccount()`). Errores del servicio: `USER_NOT_FOUND`, `EMAIL_IN_USE`, `DOCUMENT_IN_USE`, `USERNAME_IN_USE`, `INVALID_USER_DATA` (con el mensaje del servidor), `USERS_FORBIDDEN`. La pantalla (rehecha el 2026-10-28 con las piezas `ui-` porque Paola dijo que no daba buena experiencia) es una sola tarjeta: encabezado con ícono, «N registrados» y los botones «Plantilla», «Importar Excel» y «Agregar usuario» (`ui-btn`); cuatro indicadores (Usuarios, Activos, Inactivos, Importados de Excel: número grande, un clic filtra por eso y otro lo quita, «Usuarios» quita todos los filtros; `kpis`, `applyKpi()`); una fila con el buscador y los filtros Rol, Origen y Estado (desplegables comunes, cada opción con su conteo, «Analista (1)»), «Mostrando los N usuarios» / «N de M encontrados» y «Reiniciar filtros»; y **una sola tabla** (`ui-table`, encabezado una vez, pasa a fichas en pantallas angostas) con un `<tbody>` por rol (`roleSections`): su fila de grupo con el nombre del rol y «1 usuario · 1 activo · 0 inactivos» (singular y plural), y las columnas Usuario, Registro, Permisos y Acciones (ver detalle, editar, "Rol y permisos" e interruptor de estado, que pide confirmación). Los modales siguen con sus estilos propios. **Permisos:** el backend no guarda permisos por usuario; `permissionsOf(rol)` (en `usuarios.model.ts`, la misma tabla por rol del front original) solo se muestra ("6 / 11", detalle y diálogo de rol): para cambiarlos se cambia el rol. Un usuario nuevo empieza como Ciudadano (`DEFAULT_USER_ROLE`). El encabezado muestra cuántos hay registrados, "Plantilla" (`template()`, `GET /usuario/plantilla`, el Excel vacío con las columnas Nombre y apellido, Correo, Cédula y Rol) e "Importar Excel" (`importExcel()`, `POST /usuario/upload-excel` con el campo `file`): el servidor lee la primera hoja, crea las cuentas con la cédula como contraseña temporal (sin rol quedan Ciudadano; un rol que no existe se cambia y se avisa), se salta las que ya existen y responde `{ totales, exitosos, conContrasenaTemporal, errores, avisos }`, que se muestra en un diálogo (filas con error y filas importadas con cambios) antes de recargar la lista; un archivo que no es Excel lo responde como 0 de 0. El detalle de un usuario muestra su cédula y si sigue con la contraseña temporal. No se copió el asistente del original que asigna el rol fila por fila en el navegador (necesita la librería `xlsx` en el front): el rol se corrige después en "Rol y permisos". Filtro por origen (`User.origin`: `Excel` si el backend dice `EXCEL`; lo demás —`MANUAL`, `SEED`— es `Manual`). `PerfilComponent` recibe `[profile]` y emite `profileSaved` (el shell actualiza la tarjeta del menú y el nombre de la sesión con `AuthService.renameSession()`) y `cancel`. Tiene el contenido del front original en dos columnas (diseño pedido por Paola el 2026-10-19): a la izquierda la tarjeta de identidad (foto o iniciales, botón "Subir foto"/"Cambiar foto" con la nota "JPG, PNG o WEBP. Máximo 2 MB", "Quitar foto", nombre, correo, píldoras de rol, nivel de acceso según el rol y "En línea", y bajo un divisor Entidad = `PROFILE_ENTITY`, Fecha de vinculación = `dateJoined`, "Último acceso" = inicio de esta sesión, `SessionStore.startedAt()`, y los tres indicadores); a la derecha las pestañas Perfil | Seguridad con tarjetas de encabezado con ícono, etiquetas en mayúscula pequeña y el correo y el "Rol en plataforma" de solo lectura con candado; pestaña "Perfil" ("Información personal" e "Información institucional") y pestaña "Seguridad" (cambio de contraseña; antes se llamaba "Configuración" y se confundía con el modal de Configuración). De acuerdo al backend: id y rol salen de `GET /auth/me`; nombre y apellido (un solo campo, "Nombre y apellido"), teléfono, descripción profesional y foto, de `GET /api/mi-cuenta/perfil`, y se guardan con `PATCH /api/mi-cuenta/perfil` (`{ nombreApellido, telefono, descripcion, avatar }`; la foto es un data URL de hasta 2 MB y `avatar: null` la quita): **cualquier rol edita su propio perfil**; si el servidor rechaza algo (p. ej. la foto) se muestra su motivo (`PROFILE_INVALID`). La fecha de creación sale de `GET /usuario/:id`, que solo responde al administrador y al analista (para los demás queda vacía). El correo no se edita (identifica la cuenta). La contraseña se cambia con `PATCH /auth/change-password` a través de `AuthService.changePassword()` (su 401 significa "contraseña actual equivocada" y por eso el interceptor no lo trata como sesión vencida; un 400 trae el motivo del servidor —igual a la actual, datos personales, clave común—, que se muestra con `passwordChangeError()` de `shared/format/password.ts`). Versiones anteriores guardaban la foto y la descripción en localStorage (`photoStorageKey()`, `descriptionStorageKey()`): si el servidor aún no las tiene se muestran las de este navegador y, al guardar, suben al servidor y se borran de aquí. Lo que el backend no tiene: los tres indicadores se muestran con "—" y Regional y Centro con "Sin registrar" (no se inventan valores); el Área es el texto del proyecto `perfil.instAreaValue`; Cargo y Rol son el rol de la cuenta. La configuración del sistema vive en `SettingsService` (signals), no en `AppComponent`.

**Vistas.** Están en `src/app/views/<nombre>/` (las del menú del proyecto más las comunes `usuarios`, `perfil` y `login`). Cada una tiene su componente standalone (`.ts`/`.html`/`.css`/`.spec.ts`, formularios template-driven con `FormsModule`), un **modelo** (`<vista>.model.ts`: tipos de dominio y funciones puras) y un **servicio** (`<vista>.service.ts`, ver "Capa de servicios"). **Cada subcomponente va en su propia subcarpeta** de la vista, con su `.ts`/`.html`/`.css`/`.spec.ts` y su modelo si lo tiene (p. ej. `actualizacion-cno/carga-cno/`, `actualizacion-cno/ocupacion-wizard/`, `actualizacion-cno/editar-ocupacion/`, `actualizacion-cno/option-picker/`, `actualizacion-cno/catalog-selector/`, `actualizacion-correlativa/carga-correlativa/`, `actualizacion-correlativa/catalog-panel/`, `analisis/analisis-editor/`, `reportes/reporte-detalle/`, `reportes/reporte-estadisticas/`, `validaciones/validacion-editor/`); en la carpeta de la vista quedan su componente principal, modelo, servicio, doble de prueba y lo que comparten sus subcomponentes (p. ej. `actualizacion-cno/clasificacion.ts`). **HTML semántico:** encabezados de modal, tarjeta o panel en `<header>`, barras de acciones del pie en `<footer>`, la paginación en `<nav>`, contenido independiente en `<article>`/`<section>`, datos tabulares en `<table>`; `div` solo para agrupar por diseño. Lo que se abre con clic también se abre con teclado (un `<button>` o, en una fila de tabla, `tabindex="0"` con Enter y Espacio). Los `div` que el CSS selecciona por etiqueta (`.cc-figures div`, `.i2-info > div`, `.analisis-facts > div`…) no se cambian sin ajustar ese CSS. **Comentarios:** cada clase lleva un JSDoc que dice qué es, y cada método con lógica uno que explique el porqué o el efecto (qué pide al servidor, qué valida, qué pasa si falla); no se comenta lo que el nombre ya dice. El componente re-exporta su modelo (`export * from './<vista>.model'`), así que los tipos se pueden importar desde cualquiera de los dos. Las fechas se guardan y muestran como texto tal como las daría la base de datos (`DD/MM/YYYY hh:mm AM/PM`).

**Capa de servicios.** Los componentes nunca llaman al backend ni validan datos "de servidor": todo pasa por el servicio de su vista, que devuelve `Observable`. El servicio real usa `HttpClient` y traduce los DTO del backend (declarados como interfaces privadas en el propio servicio) al modelo de la vista; `src/app/shared/api/http-helpers.ts` tiene lo común (`ApiPage`, `queryParams()` que omite los valores vacíos porque el backend rechaza parámetros que no espera, `downloadName()`, `isNotFound()`). Los errores se traducen a códigos estables (`OCCUPATION_NOT_FOUND`, `INVALID_CREDENTIALS`…) que el componente explica. **Todos los servicios de las vistas construidas ya consumen el backend:** `AuthService`, `PerfilService`, `UsuariosService`, `InicioService`, `CnoService`, `CuocService`, `CorrelativaService`, `AnalisisService`, `ComparativaService`, `Instrumento2Service`, `Instrumento3Service`, `ActualizacionCnoService`, `ActualizacionCorrelativaService`, `ValidacionesService` y `ReportesService`. No queda ningún dato de ejemplo en la app (solo en los `*.testing.ts`).

**Análisis → Comparativa → Instrumento 2 (según el backend).** El buscador de Análisis muestra en cada resultado el código, el nombre y debajo «CNO · área de desempeño» o «CUOC · área de cualificación», como la versión desplegada (el área ya viene en la consulta de cada catálogo; `AnalysisSearchResult.area`). Análisis nunca modifica el catálogo: `AnalisisService.save()` hace `POST /api/analisis/guardar` con las 2 o 3 ocupaciones editadas en los espacios `cno`, `cuoc` y `relacion` (son solo posiciones: cada uno acepta CNO o CUOC) y `panelSeleccionado: 'left'` (la primera es la principal); el backend crea una copia de cada ocupación (código `<original>-<comparativa>-<posición>`) y un "instrumento 2" en estado `PENDIENTE`. **Una comparativa es ese instrumento 2**: `ComparativaService` lee `GET /api/instrumento2` (lista completa, sin filtros ni páginas: búsqueda, filtro, paginación y resumen se resuelven en el front sobre una respuesta que se reutiliza 5 s y se invalida al escribir) y `GET /api/instrumento2/:id/comparacion` (las ocupaciones completas). Estados del backend → los de la pantalla: `PENDIENTE` Recibido; `EN_REVISION` y `AJUSTES_SOLICITADOS` Editado; `GUARDADO` En Instrumento 2; `VALIDADO` Diligenciado; `ENVIADO_EXPERTO` y `APROBADO_FINAL` Enviado. El detalle ("Ver") es el de la versión desplegada (clases `cpv-`, actualizado el 2026-10-21 con las imágenes de Paola): encabezado con Volver, título, ocupaciones, datos, estado y "Editar"; pestañas en píldoras; una tarjeta por ocupación (01, 02…) con la columna "Comparación" después de la primera (aspectos verde/naranja que abren su pestaña); barra fija abajo con el estado de los cambios. "Editar" (el general o el de una tarjeta, que queda resaltada) pasa a modo edición: nombre, nivel y área (desplegables de `AnalisisService.options()`, con copias), descripción, la observación y las cinco listas (texto editable, × para quitar, "+ Agregar" con `OptionPickerComponent` y los catálogos de `ActualizacionCnoService`; en denominaciones agrega una fila "Nueva"). `saveChanges()` = un `PATCH /api/instrumento2/:id` por ocupación cambiada, en orden, con `codigoOcupacion` (la copia, `AnalysisOccupation.copyCode`), datos y las cinco listas (el backend las reemplaza juntas y relaciona los elementos sin código por su texto; al reemplazar, reordena las funciones CUOC). En la tarjeta CUOC la lista de habilidades se titula «Destrezas» (`listTitleKey()`), como en el resto de la app; lo mismo en el detalle de Instrumento 2 (`sectionLabelKey()`). Nivel y área se muestran como en Análisis (pedido por Paola el 2026-10-26), también en el detalle de Instrumento 2: en la CNO «Nivel de cualificación: Nivel 1 (A) - Profesionales, Dirección y Gerencia» (`levelText()` con `codNivelCualificacion`, que `toOccupation()` toma solo en la CNO) y «Área de desempeño»; en la CUOC «Nivel de competencia: Nivel 4» (su código, 4, ya va en el nombre) y «Área de cualificación». El desplegable de nivel en edición muestra el código pero guarda el nombre, que es como lo busca el servidor. Se validó que el nivel (nombre y código) y el área de cada copia coinciden con su ocupación original en las cinco comparativas. Tarjetas ordenadas (pedido por Paola el 2026-10-26): nombre, nivel y área van uno debajo del otro con todo el ancho, en vista y en edición (en tres columnas se partían en muchas líneas); las cajas parten una palabra solo si no cabe sola (`overflow-wrap: break-word`, no `anywhere`); las tarjetas comparten filas de la cuadrícula (`grid-template-rows: subgrid`), así los encabezados miden lo mismo aunque un nombre ocupe más renglones y el contenido empieza a la misma altura; no tienen desplazamiento propio (crecen y se desplaza la página) y la columna «Comparación» queda fija (`position: sticky`) al bajar, salvo hasta 1100px, donde todo va en una columna. Comprobado midiendo en la app a 1500 y 1920 px. **Configuración.** Está en `src/app/settings/`: `SettingsComponent` (pestañas con patrón tablist, vista previa en vivo y confirmaciones de Guardar/Restablecer) más un componente standalone por pestaña en `tabs/` (apariencia, logos, idioma, acerca de). Las pestañas usan formularios reactivos cuyos cambios van directo a `SettingsService.updateDraft()`. Sus estilos compartidos están en `_settings-shared.scss`, que cada pestaña incluye con `@use` (por eso se emite una vez por pestaña). Los tipos y las listas de opciones están en `settings.model.ts`. El modal es un panel de vidrio: `.configuration-modal` (en `app.component.css`) es translúcido con `backdrop-filter` sobre un fondo que deja ver la vista desenfocada, mide como el del proyecto de referencia (`Downloads/tdo-sena-dev 1/codigo-configuracion`): máximo 1150px de ancho y 85vh de alto, blanco al 70 % con desenfoque de 40px, radio 24px; no lleva relleno: cada franja de `SettingsComponent` pone el suyo (encabezado, dos columnas separadas por una línea —lo editable en dos tercios y la vista previa en un tercio— y pie con Restablecer a la izquierda y Guardar a la derecha). Sin `backdrop-filter` o con alto contraste el panel vuelve a ser opaco. Hasta 880px todo baja en una sola columna que se desplaza.

**Configuración: borrador vs. guardado.** `SettingsService` mantiene `saved` (persistido en `localStorage` bajo la clave `tdo_system_config`) y `draft` (lo que se está editando). **El borrador solo se ve en la tarjeta de vista previa de Configuración** (`SettingsComponent.previewVariables()` le pone los colores y la escala de texto del borrador en su `style`, y las clases `preview-dark` / `preview-contrast` y `data-density` hacen el resto); la interfaz (shell, ingreso, idioma, logo del menú, favicon) usa siempre `saved` y cambia solo al guardar.
- `save()` persiste el borrador y falla con `STORAGE_FULL` si se supera la cuota de almacenamiento.
- `discardDraft()` vuelve a lo guardado.
- `reset()` vuelve a los valores de fábrica (`DEFAULT_SETTINGS`) y los guarda de inmediato con `save()`; no requiere pulsar "Guardar cambios".

`ThemeService` es el único lugar que toca el DOM global para el tema: variables CSS (`--primary-color`, `--accent-color`, `--type-scale`, …), los atributos `data-density` / `data-high-contrast` en `document.documentElement`, y el favicon. El modo oscuro es `saved().theme === 'oscuro'`, que se refleja como la clase `.dark-mode` en el div raíz del shell; el botón de luna de la barra superior guarda el tema directamente.

**Estilos compartidos.** `src/styles/ui.css` (importado al inicio de `styles.css`) tiene las piezas visuales reutilizables con prefijo `ui-`: página y encabezado, pestañas, tarjetas, botones, campos, interruptor, avisos, etiquetas, estados vacíos, tablas, paginación, menú contextual y modales, con su modo oscuro y su respuesta a la densidad y al alto contraste de Configuración. Tablas adaptables: `ui-table-responsive` en el `.ui-table-wrap` (más `-md` o `-lg` según cuántas columnas tenga) y `[attr.data-label]` con el título de la columna en cada `<td>`; cuando el contenedor mide menos que el umbral (45em / 60em / 71.875em, por container query; con el texto normal 720 / 960 / 1150px), cada fila pasa a ser una ficha con sus datos apilados, sin desplazamiento horizontal. Los umbrales van en em para seguir el tamaño de texto de Configuración: con letra más grande se pasa a fichas antes en vez de desbordarse (el ancho de la página tiene un máximo, ~1230px de tabla). Una tabla con muchas columnas (como Instrumento 2) deja las columnas a la medida de su contenido (`width: 1%` y sin saltos) y la de texto largo con todo el resto (`width: 100%; max-width: 0`, recorta con «…»), solo en modo tabla (`@container (width > umbral)`): así ningún ancho depende de la fuente. Se verifica midiendo en el navegador **con Work Sans cargada** (las pruebas no la tienen: la carga `instrumento-2.layout.spec.ts`; con otra fuente las medidas engañan). La paginación es igual en todas las vistas porque es un solo componente (`PaginationComponent`, ver "Compartido"): una sola frase "Mostrando {{from}} a {{to}} de {{total}} <registros|ocupaciones|comparativas>" a la izquierda, opciones de "por página" 8, 16 y 32 (empieza en 8) y, a la derecha, anterior, números de página (hasta cinco, `.ui-page-btn` con `.active`), siguiente y el selector "N por página" (el desplegable común con la clase `ui-page-size`, más bajo; al estar al pie, su lista se abre hacia arriba). **Desplegables: nunca un `<select>` nativo.** Todos son `<app-filter-combobox>` (pedido por Paola el 2026-10-28: "todos tienen que estar igual que en Consulta CNO"), también en Usuarios y la paginación. Todos los modales (`.ui-modal`, los `.confirm-dialog` de Usuarios y Configuración, y el panel de Configuración) usan el mismo radio `--modal-radius` (24px, en `styles.css`), más redondeado que tarjetas y botones (`--border-radius`, 16px); si un modal no cabe en la ventana se desplaza su fondo (`.ui-modal-backdrop` / `.dialog-backdrop` con `overflow-y: auto` y el modal centrado con `margin: auto`), no el modal, para que su barra no tape las esquinas (barra delgada; mientras hay un modal abierto la página de fondo no se desplaza —`html:has(...)` en `styles.css`— para que no se vean dos barras); los modales con encabezado y pie fijos usan `.ui-modal-fixed` (alto máximo de la ventana y solo su cuerpo se desplaza por dentro: el asistente de ocupación y el detalle de Análisis). **Regla del sistema visual (Figma "Ecosistema visual nivel fábrica", fijada en Configuración):** solo Work Sans con pesos 400 y 600 (`var(--fw-regular)` / `var(--fw-semibold)`, nunca 700/800 ni otra fuente: los controles heredan con `font: inherit`), títulos 26 / subtítulos 20 / párrafos 16, colores de marca y los tres estados (`--state-ok|error|warn-*`), y un solo radio "Suave": botones, campos, tarjetas y cajas usan `var(--border-radius)` (16px), los modales `var(--modal-radius)`; los botones de solo ícono son circulares y las píldoras/chips 999px. No se escriben radios en px en botones, campos ni tarjetas (solo en adornos pequeños: anillos de foco, barras, franjas, muestras de color). Las vistas nuevas se arman con esas clases y su `.css` propio solo lleva lo específico; no se crean botones, modales ni campos con estilos propios. **Seguridad.**
- **Sesión en cookie httpOnly.** `POST /auth/login` recibe `{ identifier, password }` (más `portal: 'ape'` solo en el acceso APE, que este front no tiene) y responde `{ user: { id, email, usuario, nombreApellido, telefono, role, debeCambiarContrasena } }`; el token JWT (firmado por el servidor con `JWT_SECRET`; lleva `idusuario`, `correo` y `rol`) viaja en la cookie `olo_sesion` (httpOnly, SameSite=Lax, `Secure` con `COOKIE_SECURE=true`), que JavaScript no puede leer: un script ajeno no puede robarlo. `SessionStore.start(account, remember)` guarda solo quién ingresó y traduce el rol del backend a su nombre en el front (`ROLE_LABELS` en `shared/session.ts`: `ADMINISTRADOR` → `Administrador`, `ANALISTA` → `Analista`, `EXPERTO`, `CIUDADANO`, `APE`, `TENDENCIAS_OCUPACIONES`). Los permisos reales los decide siempre el servidor, que además vuelve a leer el estado de la cuenta en cada llamada (una cuenta desactivada deja de servir al instante). El navegador no sabe cuándo vence la cookie: al recargar, el shell confirma la sesión con `AuthService.refresh()` (`GET /auth/me`) y cualquier 401 la cierra como vencida. "Cerrar sesión" = `POST /auth/logout`, que revoca el token en el servidor (una copia ya no sirve) y borra la cookie; aunque no responda, la sesión se olvida en el navegador.
- **Interceptor** (`auth.interceptor.ts`, registrado en `app.config.ts`): no agrega cabeceras (front y API comparten origen: proxy de `ng serve` en desarrollo, Nginx en producción, así que la cookie viaja sola). Sobre las rutas del backend (`/api/`, `/auth/` y `/usuario`, las mismas de `proxy.conf.json`): un 401 cierra la sesión como vencida (salvo en el ingreso, el cambio de contraseña y la salida) y un 403 con `codigo: 'CAMBIO_CONTRASENA_REQUERIDO'` pasa la sesión al cambio obligatorio (`requirePasswordChange()`).
- **Contraseñas.** Nunca se guardan ni se devuelven: `User` no tiene `password` y `UserDraft` tampoco (la inicial es la cédula). El servidor guarda bcrypt (costo 12) y aplica su política (`back/src/common/utils/politica-contrasena.ts`: 8 a 64 caracteres, tipos de carácter, sin claves comunes ni datos personales); el front valida lo que puede saber sin el servidor (`isStrongPassword()`) y muestra el motivo del servidor para lo demás. La API simulada de las pruebas guarda solo el hash con sal (`MockCredentialsStore`, SHA-256). El ingreso borra la contraseña escrita después de cada intento.
- **Intentos fallidos.** El servidor responde el mismo 401 si la cuenta no existe o la contraseña no coincide (`INVALID_CREDENTIALS`, no revela qué cuentas existen; además gasta el mismo tiempo en ambos casos), 401 con otro mensaje si la cuenta está inactiva (`USER_INACTIVE`) o el correo no es del SENA (`EXTERNAL_EMAIL`), 401 con su propio motivo para otros rechazos (p. ej. un usuario APE: `LOGIN_REJECTED`, se muestra el mensaje) y 429 si se superan `MAX_LOGIN_ATTEMPTS` (10) intentos en `LOCKOUT_MINUTES` (1) minuto (`TOO_MANY_ATTEMPTS`). Si no hay respuesta del servidor (o responde 5xx), `LOGIN_UNAVAILABLE`.
- **Pendiente:** HTTPS en el despliegue (con él, `COOKIE_SECURE=true`) y token de renovación (refresh): hoy, al vencer la cookie hay que volver a ingresar.

**Control de acceso.** El rol de la sesión decide el shell: `AppComponent.sessionRole() === ADMIN_ROLE` ("Administrador") habilita todo en `app.component.html`; un rol de `ROLE_VIEWS` (en `proyecto/config.ts`; aquí `Experto: ['validaciones']`) entra con un menú que solo trae esas vistas (`filterMenu()` en `app.menu.ts`, sin Gestión de usuarios; abre en la primera, no carga la lista de usuarios y una vista fuera de su menú no se pinta), y cualquier otro rol ve la plantilla `#restricted`, que solo permite cerrar sesión (`hasShell()`). Los permisos reales los decide el backend por rol.

**Sin modo de solo lectura global.** Existió un `GlobalReadOnlyService` que simulaba `PUT /api/system/read-only` en `localStorage`; el backend no lo tiene y no tenía control en la interfaz, así que se quitó el 2026-10-21 (servicio, aviso, `writeBlocked()`, `assertWritable()` y sus pruebas) para no dejar datos simulados. Si el backend lo incorpora, se agrega como un servicio real.
